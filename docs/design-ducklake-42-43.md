# Design: DuckLake fork for inline VARIANTs and incremental compaction

Status: proposed
Scope: [thelake#42](https://github.com/softprobe/thelake/issues/42) and [thelake#43](https://github.com/softprobe/thelake/issues/43)
Baseline: branch `v0.2`, commit `5e01c34`

## Decision summary

Maintain one Softprobe DuckLake fork, pinned together with the DuckDB engine
version used by thelake. Add two engine capabilities plus one application
integration policy:

1. external-catalog inline storage for `VARIANT`, with a versioned lossless
   wire encoding, a safe reader, and an inline VARIANT statistics surface;
2. add only the missing native TWCS policy to DuckLake's existing compactor,
   using upstream `newer_than` for incremental candidate selection;
3. write metrics directly to the #43 canonical raw metric table family and
   populate explicit 5m/1h/1d rollup levels asynchronously.

Keep the application responsible for selecting *when* maintenance runs and
for supplying policy configuration. Move row/file selection, partition
locality, output sizing, and snapshot publication into DuckLake.

The public API should be additive. Preserve the current behavior of
`ducklake_merge_adjacent_files` and consume its upstream `newer_than` option.
The new thelake work is a durable per-scope/table watermark, safe retry,
observability, metric rollup, and query-routing integration—not a second
file-selection algorithm. A full compaction remains an explicit
repair/bootstrap operation.

This follows official DuckLake prior art: upstream PR
[#1363](https://github.com/duckdb/ducklake/pull/1363) added `newer_than` to
`ducklake_merge_adjacent_files` for append-heavy time-series maintenance.

### `record_date` and the partitioning invariant

`record_date` is the UTC calendar date derived from each metric's event
`timestamp` (`DateTime<Utc>::date_naive()`), stored as an Arrow/DuckLake
`DATE` (`Date32`). It is a physical column used for date filtering and the
intended partition key; it is not a DuckLake partition merely because it is
present in the schema. The target policy is strict: an OTLP data point with
`time_unix_nano = 0` or an out-of-range timestamp is rejected as an invalid
request; it is never assigned the wall-clock ingestion time.

The writer validates that one Arrow batch contains one date, groups mixed-date
requests by UTC `record_date`, and uses `ORDER BY record_date, metric_name,
timestamp` before `INSERT`. Each date is written as a partition-aligned Arrow
batch inside the catalog write flow, so a mixed-date request cannot put a row
in the wrong partition. Invalid timestamps are rejected before any group is
published. The CTAS bootstrap in `src/storage/ducklake/writer.rs` now executes
`ALTER TABLE ... SET PARTITIONED BY (record_date)` for `metric_samples` before
the insert, establishing the #43 partition invariant for a clean catalog.

DuckLake's supported operation is `ALTER TABLE tbl SET PARTITIONED BY
(record_date)`. It affects new writes; it does not repartition files already
written under an older partition specification. See the [official partitioning
documentation](https://ducklake.select/docs/stable/duckdb/advanced_features/partitioning).
New target tables must be created, partitioned, and only then receive their
first data. A catalog with an old schema is unsupported and must be reset
rather than repaired in place. The current parser
converts a missing/invalid
timestamp to `Utc::now()`: this can put a late or malformed point in the wrong
date partition. The target parser rejects that point before deriving
`record_date`. For rollups,
`record_date` is always `UTC date(bucket_start)`, never ingestion time.

### DuckLake fork points

The local upstream checkout is `/tmp/softprobe-ducklake-fork`.

- `src/metadata_manager/postgres_metadata_manager.cpp` and
  `src/metadata_manager/sqlite_metadata_manager.cpp` currently mark
  `VARIANT` as non-native and disable inline support for it.
- `src/common/ducklake_util.cpp::ToSQLString` explicitly throws for a
  VARIANT when the metadata backend is not native.
- `src/storage/ducklake_inline_data.cpp` already computes inline column stats
  and emits them through the staged commit path, but its generic stats walker
  excludes VARIANT from recursive processing.
- `src/storage/ducklake_inlined_data_reader.cpp` reads external-catalog
  inline columns through SQL and then transforms the result into DuckDB
  vectors. This is the correct place for a codec-aware decode step; changing
  Softprobe SQL alone would leave other DuckLake readers unsafe.
- `src/functions/ducklake_compaction_functions.cpp` already groups candidate
  files by schema version, `partition_id`, and partition values. Upstream PR
  #1363 adds `newer_than` to the candidate query; there is no need to add a
  second file-rewrite implementation. The missing native TWCS policy remains a
  deliberate fork feature because upstream does not provide it.

One important correction to #42: a flush-through request still publishes one
snapshot whether its rows go to Parquet or inline metadata. Inlining can
materially reduce Parquet files, file metadata, object-store I/O, and later
cleanup work, but it cannot reduce snapshot count without changing commit
coalescing semantics.

## #42: external-catalog VARIANT inlining

### Storage contract

Use the existing per-table, per-schema-version inline tables. For a logical
`VARIANT` column:

- DuckDB metadata continues to describe the logical type as `VARIANT`.
- PostgreSQL stores the physical value as `BYTEA`; SQLite stores it as
  `BLOB`.
- The value is a versioned `DLV1` canonical typed-JSON envelope stored in
  that backend-compatible scalar. The envelope is JSON for inspectability,
  but its explicit type tags make it lossless; it is not ordinary untyped
  JSON.
- The envelope must preserve NULL, scalar logical type, object field names,
  arrays, nested values, numeric types, and the distinction between a typed
  value and an untyped value. Do not use raw DuckDB vector memory or an
  unversioned internal serializer as the catalog contract.

For example, a typed integer is represented by a tagged value rather than a
JSON number whose width and signedness could be lost. PostgreSQL stores the
canonical UTF-8 envelope in `BYTEA`; SQLite stores it in `BLOB`. The codec
must define canonical key ordering, number formatting, UTF-8 handling, and
maximum value size so equivalent values have stable bytes across backends.

The normative DLV1 payload is a single canonical JSON object of the form
`{"codec":"DLV1","value":<node>}`. A node is one of:

```text
{"t":"null"}
{"t":"bool","v":true|false}
{"t":"i64","v":"-9223372036854775808"}
{"t":"u64","v":"18446744073709551615"}
{"t":"f64","v":"0x<16 lowercase hex digits>"}
{"t":"decimal","v":"<canonical decimal>"}
{"t":"string","v":"<UTF-8 string>"}
{"t":"binary","v":"<lowercase base64url without padding>"}
{"t":"array","v":[<node>, ...]}
{"t":"object","v":[{"k":"<UTF-8 key>","v":<node>}, ...]}
```

Object entries are sorted by UTF-8 byte order and duplicate keys are
rejected. JSON strings use one canonical escaping form; integers and decimals
have no redundant sign/zeroes; floats preserve their IEEE-754 bits, including
NaN and infinity. SQL NULL is represented by a backend SQL NULL, while a
VARIANT/JSON null is the `{"t":"null"}` node. Writers emit only DLV1;
readers reject unknown codec versions with an upgrade error. Add golden
byte-level vectors for every node type, empty containers, SQL NULL, VARIANT
null, malformed JSON, invalid UTF-8, duplicate keys, and numeric boundaries.

### Engine changes

Add a small `DuckLakeVariantCodec` layer in the fork and use it from both
external metadata managers.

1. `PostgresMetadataManager::SupportsInlining` and
   `SQLiteMetadataManager::SupportsInlining` return true for VARIANT only
   when the fork's codec capability is enabled.
2. `GetColumnTypeInternal(VARIANT)` maps to `BYTEA` for PostgreSQL and
   `BLOB` for SQLite. The logical DuckLake column metadata remains VARIANT.
3. Replace the VARIANT branch in `ToSQLString` with a codec-produced backend
   scalar literal. Use the existing backend-safe bytea/blob literal helpers;
   never interpolate the encoded envelope as ordinary SQL text.
4. Add a metadata-manager projection hook for inline reads. A VARIANT
   projection reads the raw physical bytes, not `CAST(bytea AS VARIANT)`.
5. Extend `TransformInlinedData` to decode the physical BLOB/BYTEA vector into
   a DuckDB VARIANT vector before the normal reader/filter path. Validate
   envelope version and length, reject malformed values with a normal
   DuckLake read error, and never allow a malformed row to invalidate the
   DuckDB connection.
6. Keep the existing Parquet VARIANT path unchanged. A table can therefore
   have Parquet-backed and inline-backed rows with the same logical schema.
7. Add a catalog capability marker (for example, a DuckLake tag or metadata
   capability row) identifying `variant_inline_codec = DLV1`. A stock
   DuckLake extension must fail fast with an actionable compatibility message
   rather than silently returning bytes as VARIANT. The fork should continue
   reading catalogs that have no marker and no inline VARIANT rows.

The `VARIANT` capability must be decided from the active metadata manager,
not just from the DuckDB catalog type. This keeps PostgreSQL and SQLite
behavior aligned and prevents a future catalog backend from accidentally
claiming support.

### Inline statistics

Reuse the existing `DuckLakeColumnStats.extra_stats` representation and the
existing `DuckLakeColumnVariantStats` serialization format. Refactor the
variant-stat collector so both Parquet footer stats and inline stats use the
same field-path, type-consistency, null, min/max, and fully-shredded rules.

Add a catalog table with a stable, source-specific key rather than overloading
`ducklake_file_variant_stats`'s `data_file_id` foreign key. Allocate one
`inline_data_id` per committed inline append/fragment and make its snapshot
visibility explicit. Add the reserved physical column
`__ducklake_inline_data_id` to each inline table; it is projected out of the
logical schema and has the same value for every row in one append fragment.

```text
ducklake_inlined_variant_stats
  table_id
  inline_data_id
  inlined_table_name
  schema_version
  partition_id / partition values (nullable for v1)
  begin_snapshot
  end_snapshot (nullable)
  column_id
  variant_path
  shredded_type
  min_value / max_value
  null_count / value_count
  contains_nan
  stats_version
```

The corresponding `ducklake_inlined_data` metadata row is the authoritative
fragment record:

```text
inline_data_id (primary key)
table_id / inlined_table_name / schema_version
begin_snapshot
end_snapshot (nullable)
row_count
stats_exact (boolean)
```

Index fragment metadata by `(table_id, begin_snapshot, end_snapshot)` and
stats by `(inline_data_id, column_id, variant_path, stats_version)`. For a
requested snapshot `s`, a fragment is visible iff
`begin_snapshot <= s AND (end_snapshot IS NULL OR s < end_snapshot)`. The
reader joins stats through that predicate and unions only visible fragments
with visible Parquet files. A normal append allocates the ID, inserts its
rows, fragment metadata, and stats, then publishes `begin_snapshot` in one
catalog transaction. A delete/update writes a new snapshot and either closes
the whole fragment with `end_snapshot` or marks it `stats_exact = false` when
only part of the fragment changed; historical rows and metadata are never
mutated.

Rows and their inline-fragment stats are inserted/closed atomically in the
same catalog commit. Expose a read-only union view,
`ducklake_variant_stats`, over Parquet and inline sources; select the inline
fragments visible to the requested snapshot. Keep
`ducklake_file_variant_stats` backward compatible.

Reuse `PartialVariantStats` merge rules for both sources, including
conservative dropping of paths whose logical types are incompatible. The
first implementation should use inline stats for observability and safe
coarse pruning only. Min/max stats over a superset of rows are safe after
deletions, but null/value counts are not. Do not use null-count pruning for an
inline table unless the fragment stats are visible for the requested snapshot
and the live-row semantics are proven. Missing or stale inline stats must
disable pruning, never produce a false negative.

### Read/write behavior and tests

Softprobe's Rust writer should not grow a second inline writer. It should keep
the current `CREATE TABLE ... AS SELECT ...` and `INSERT ... BY NAME` path,
with only the fork changing the inlining decision and codec handling.

Replace the current assertions in
`inlined_data_stays_readable_across_maintenance` with a shared contract that
runs as mandatory CI jobs against both SQLite and PostgreSQL catalogs. The
same fixtures, setup, assertions, and maintenance scenarios must be reused;
only catalog startup and connection configuration are backend-specific:

- small `traces`, `logs`, and canonical metric-table batches inline and create
  no data Parquet file;
- the physical inline column is BLOB/BYTEA while `DESCRIBE` through DuckDB
  reports logical VARIANT;
- strings, booleans, typed integers/floats, arrays, objects, empty arrays,
  NULL, and malformed-codec rejection round-trip;
- equality filters, nested label projection, `COALESCE(CAST(... AS
  VARCHAR))`, and JSON projection return the same rows for inline and
  Parquet-backed fixtures;
- reads and writes remain valid before and after snapshot maintenance;
- `ducklake_inlined_variant_stats` contains the same hot paths and logical
  types as `ducklake_file_variant_stats` for equivalent fixtures;
- legacy MAP tables still fail fast and are not silently replaced.

The codec golden vectors are a separate backend-independent unit suite, and
the contract suite must include both old-reader capability rejection and
missing/stale-stat conservative behavior.

Add a test that deliberately mixes inline and Parquet rows for one table and
compares query results, because that is the production transition state.

## #43: incremental partition-preserving compaction

### Decision

Use upstream `ducklake_merge_adjacent_files(...,
newer_than => TIMESTAMPTZ)` as the candidate-age primitive, but retain the
actual #43 TWCS requirements in the DuckLake fork: one-day event-time windows,
open/closed-window policy, file-count triggers, target output size, and strict
cross-window isolation. Upstream `newer_than` maps the timestamp to a snapshot
boundary and pushes `begin_snapshot >= boundary` into the catalog candidate
query; it does not implement TWCS by itself.

The fork therefore adds a native TWCS policy to DuckLake's existing compactor,
not a second application-side compactor. The application supplies the table,
watermark, and schedule. DuckLake owns candidate grouping, window state,
partition locality, output sizing, and snapshot publication. If this policy is
not accepted upstream, #43 should remain a separate Softprobe fork feature;
`newer_than` alone is not a valid substitute for the issue's open/closed-window
and file-count guarantees.

This is not a semantic downsampling operation: TWCS rewrites the same logical
rows into fewer Parquet files and preserves DuckLake snapshot behavior.

### API

The thelake executor should call the fork's additive TWCS form of the official
function after the runtime has been upgraded to a DuckLake build containing
upstream `newer_than` plus the fork's TWCS parameters:

```sql
CALL ducklake_merge_adjacent_files(
  'catalog', 'metric_samples_5m',
  schema => 'main',
  newer_than => TIMESTAMPTZ '2026-09-01 00:00:00+00:00',
  strategy => 'twcs',
  time_partition_column => 'record_date',
  time_window => INTERVAL '1 day',
  trigger_file_num => 2,
  max_output_file_size => '64MB',
  open_window_policy => 'cap',
  open_window_max_files => 20,
  max_compacted_files => 256
);
```

The TWCS parameters above are fork/API design, not currently available in
upstream DuckLake. The implementation must reuse DuckLake's existing
candidate grouping and rewrite machinery. For each one-day `record_date`
window, a closed window compacts when its live-file trigger is met and targets
one file (or more when the target size requires it); an open window is only
reduced to the configured soft cap. No rewrite may combine two windows.
`newer_than` limits the eligible file-creation range; it does not define the
event-time window. The fork takes one candidate snapshot at call start and
performs the window scan and any bounded internal chunks against that fixed
candidate set inside one logical TWCS call. Files created after that snapshot
are left for the next watermark pass. Thelake must not repeat calls as a
per-day/per-wave loop. If an engine safety limit prevents a complete pass, the
call reports `complete = false`; the application retains its watermark and
retries the table on a later scheduled pass, without retaining an application
file inventory or cursor.

The window is the half-open UTC calendar interval `[record_date,
record_date + 1 day)`. The window containing the current UTC date is open;
earlier windows are closed. The native call returns one row per table with
`schema_name`, `table_name`, `candidate_snapshot`, `windows_processed`,
`files_processed`, `files_created`, `complete`, `status`, and nullable
`error_code`. `files_processed` counts candidate files evaluated, not rows;
`files_created` counts replacement files committed. `status` is one of
`COMPLETE`, `BUDGET_EXHAUSTED`, or `NOOP`; `complete` is true only for
`COMPLETE`/`NOOP`, and false for `BUDGET_EXHAUSTED`. A DuckLake transaction
error returns an error rather than a successful result row, and never advances
the application watermark. A later call safely re-enumerates the same
inclusive range. `max_compacted_files` is an internal per-call budget and
never authorizes the application to implement waves.

The watermark is per DuckLake scope and table. At the start of each run,
capture a UTC `run_started_at` fence before candidate enumeration. Pass the
previous watermark to `newer_than`; after the native TWCS call reports a
complete pass, persist `run_started_at` as the next inclusive lower bound.
Because the official API has a lower-bound filter but no upper-bound parameter,
the fork's logical TWCS call owns its internal bounded chunks against its
candidate snapshot. Thelake must not implement a repeated application drain
loop. If the native call reports incomplete, leave the old watermark in place
and retry the table later. Files created after the candidate snapshot are not
hidden by advancing to `run_started_at`; they remain eligible for the next
inclusive pass.
Use a one-time full pass to bootstrap old fragmentation, and use an explicit
full pass later for repair or recovery.

### Incremental compaction invariants

The upstream `newer_than` filter is based on file creation time, not the
event's `record_date`. The following rules keep it aligned with thelake's
“do not touch finalized data” goal:

1. Every time-series sample table in the target registry must be partitioned
   by `record_date` (or its documented equivalent). The raw writer batches
   metrics by `record_date`, orders rows by `record_date`, metric name, and
   timestamp, and establishes the explicit DuckLake partition spec before the
   first insert. Rollup-table initialization must apply the same invariant.
   Non-time-series index tables such as `metric_postings` must have their own
   documented partition/compaction contract; they must not inherit this
   assumption accidentally.
2. Pass the last successful watermark to `newer_than`. Only files created at
   or after that boundary are candidates; previously finalized inputs older
   than the watermark are not inputs to the incremental merge. Drain all
   compaction work exposed by that range before advancing the watermark. The
   inclusive boundary makes retry safe.
3. Keep DuckLake's existing grouping by exact partition identity and schema
   compatibility. Never rely on the application to emulate partition-local
   selection or parse storage paths.
4. A new file for an old `record_date` is a late arrival. Incremental mode
   may compact it with other newly created files in that partition, but must
   not pull the old finalized file back into the merge. This can leave more
   than one file in that partition by design.
5. Apply the configured target size and any engine safety bound as DuckLake
   options. The native TWCS call may chunk internally, but the application
   must not repeat calls for waves or partitions. Do not advance the watermark
   when the engine reports an incomplete pass, and do not add a second Rust
   bin-packing or wave algorithm.
6. A one-time full pass is allowed for bootstrap, repair, or explicit
   defragmentation. It is not part of the recurring incremental pass.

### thelake integration

Add a per-scope/table compaction watermark to `MaintenanceConfig` and a new
small app-owned persistent maintenance-state store (no such store exists in
the current checkout). The state store is driven by a target-table registry,
not a hard-coded `traces/logs/metric_samples/scores` list. Keep this state separate
from DuckLake file metadata; it records scheduler progress, not table data.
The executor should:

- call the fork's native-TWCS form of the official
  `ducklake_merge_adjacent_files` once per opted-in target table (including
  each sample resolution that is physically stored), passing `newer_than` from
  that table's last successful watermark; the fork owns internal chunking;
- keep ordinary merge as an explicit full-pass mode for bootstrap, repair, or
  tables that do not use incremental maintenance;
- create new target metric tables with an explicit DuckLake `record_date`
   partition spec during catalog initialization; no legacy table or schema
   conversion path is supported;
- run a startup/schema validator for every registered target table, verify the
  exact partition spec before promising partition-local behavior, and fail
  closed when it is absent or incorrect;
- advance the watermark only after the native call reports a complete pass;
  if its safety bound leaves work, retain the old watermark. The inclusive
  boundary makes a retry safe;
- record files processed/created, watermark, elapsed time, and whether the
  pass was incremental or full.

Do not retain a Rust TWCS planner, per-day file inventory, or wave loop. If
the loaded extension does not expose `newer_than` and the native TWCS
parameters, fail the incremental pass with an explicit capability error rather
than silently running a full merge.

Retry behavior follows the existing DuckLake operation boundaries. The
current `execute_batch_with_serialization_retry(&Connection, ...)` helper is
not sufficient because it reuses one connection; incremental compaction must
move to a retry wrapper that owns connection open, attach, CALL, rollback, and
close. A PostgreSQL serialization/deadlock failure retries the whole CALL on
a fresh connection/snapshot, up to three attempts with 50 ms, 200 ms, and
800 ms backoff. SQLite retries only classified `BUSY`/`LOCKED` failures with
a bounded busy timeout and the same attempt limit. Each retry reopens the
transaction and lets DuckLake re-enumerate candidates; no candidate list or
partial output is reused. Codec, validation, and other errors fail
immediately.

Run snapshot expiry and orphan cleanup once per catalog scope, after the
table compaction loop. These operations are independent of the incremental
watermark and must not advance it.

### Metrics architecture and compaction boundary

The current checkout is one phase behind the intended metric architecture.
The target is a canonical metric table family:

- `metric_samples` stores the high-resolution/raw sample stream needed for
  recent queries and as the source for rollups;
- `metric_samples_5m`, `metric_samples_1h`, `metric_samples_1d`, and any
  longer levels store scalar/gauge/counter rollups;
- corresponding histogram level tables (for example
  `metric_hist_samples_5m`, `_1h`, and `_1d`) retain histogram semantics rather
  than treating a histogram as an ordinary float;
- `metric_postings` stores the series/label index and is not itself a
  downsampled sample table. Its partition and compaction key must be specified
  separately, even if it is maintained in the same maintenance run.

The #43 schema contract must define at least these fields and invariants:

- every sample/rollup row has a stable `series_id` and `segment_id`,
  `bucket_start` (the raw table uses the original sample timestamp), and
  `record_date = UTC date
  (bucket_start)`;
- raw scalar rows preserve the OTLP number kind (`as_int` versus `as_double`),
  `start_time`, `is_monotonic`, aggregation temporality, flags, and exemplar
  information; conversion to `DOUBLE` happens only at a query/rollup boundary;
- raw histogram rows preserve explicit bounds, bucket counts, count, sum,
  optional min/max, start time, temporality, flags, and exemplars; histogram
  rollups retain compatible bucket state rather than reducing to one float;
- summaries remain raw-only unless a mergeable sketch is deliberately added;
  quantiles cannot be combined safely by averaging them;
- `series_id` is derived from the canonical metric identity and final label
  set (including the existing resource/datapoint collision rule), with a
  collision-safe encoding rather than an unchecked hash-only identity;
- `segment_id` is a compatibility fingerprint over metric type, temporality,
  monotonicity, and histogram bounds. A temporality or bounds change starts a
  new segment; a cumulative reset inside a segment increments reset state
  instead of merging incompatible rows;
- each rollup level records its resolution and source coverage so a query can
  distinguish exact raw data from an approximate aggregate.

The first implementation uses the separate physical tables named above; a
future resolution-partitioned layout would require a new schema change.
The ingestion request writes only the raw target table matching the OTLP data
type (`metric_samples`, `metric_hist_samples`, or `metric_summary_samples`);
5m/1h/1d rollups and `metric_postings` updates are asynchronous workers. The
Ingestion writes the canonical raw target tables. The Prometheus backend
must receive `step_ms` and query semantics, then choose raw versus 5m/1h/1d
data. Exact queries and operators that cannot be answered from a rollup use
raw data; approximate rollup use must be explicit. Boundary stitching must
ensure the same sample is never counted twice. It must stop treating
the canonical raw/rollup tables through any compatibility alias; those tables
are the only metric read path.

The initial routing matrix is:

| Query/operator | Source | Accuracy |
| --- | --- | --- |
| instant selectors and ranges with `step < 5m` | raw scalar/histogram/summary tables | exact |
| plain gauge visualization with `step >= 5m` | deterministic level: `5m` for `5m <= step < 1h`, `1h` for `1h <= step < 1d`, and `1d` for `step >= 1d` | approximate, using `gauge_last` unless a display operator is requested |
| counter `rate`, `irate`, `increase`, `delta`, or reset-sensitive expressions | raw data in the first implementation; rollup counter state is written for a later proven implementation | exact; fail on insufficient raw retention |
| histogram quantile and bucket queries | raw histogram or compatible histogram rollup with identical bounds | exact for raw; rollup accuracy explicitly reported |
| histogram `rate`, `irate`, `increase`, or reset-sensitive expressions | raw histogram data in the first implementation | exact; fail on insufficient raw retention |
| cross-series aggregations and `*_over_time` functions | raw data in exact mode; only gauge `min/max/avg/last` may use the corresponding stored rollup state in approximate mode | exact by default; approximate only when requested |
| subqueries or operators without a declared rollup implementation | existing evaluator behavior: raw data if supported, otherwise `unsupported_feature` | never silently downsampled |
| summaries and unsupported/exponential histogram operations | raw summary data or `unsupported_feature` | never silently downsampled |

`MetricsQueryRequest` gains `step_ms`, `accuracy` (`EXACT` by default or
caller-requested `APPROXIMATE`), and the selector expression capabilities
needed by this matrix. Every selector fetch, including the prefetch path,
receives the same request context. The PromQL evaluator must propagate
`eval_range`'s step instead of discarding it before the backend fetch. Every
response carries `accuracy` and the source resolution(s) used; response
accuracy is `APPROXIMATE` if any returned segment came from a rollup and is
`EXACT` only when every segment came from raw data. An `EXACT` request never
returns a rollup result; it returns `insufficient_retention` instead. An
`APPROXIMATE` request may return `EXACT` when raw fallback was required.
Resolution stitching uses half-open time intervals and a per-level
coverage record, so a raw/5m or 5m/1h boundary cannot duplicate or omit a
sample. For an approximate gauge request, the router starts at the
deterministic level above and searches only toward finer levels (`1d -> 1h ->
5m -> raw`) when the requested coverage is incomplete; it never selects a
coarser-than-step level. Exact requests use raw throughout or return
`insufficient_retention`. If an expression is not declared compatible with a
rollup, the router uses raw data or returns an explicit
unsupported/insufficient-retention error; it never silently changes the
query's meaning.

Routing details are fixed for the first implementation. `EXACT` is the
default accuracy and `APPROXIMATE` must be requested by the caller. An instant
selector uses the newest raw sample within the configured lookback window in
exact mode; an approximate gauge selector may use a finalized rollup whose
`bucket_end` lies within that window. A range selector uses half-open coverage
and includes one raw sample before its lower bound for counter functions.
Counters, reset-sensitive functions, exact `*_over_time`, and exact
cross-series aggregations are raw-only. Approximate gauge `min/max/avg/last`
may use the matching stored state. Histogram rows are expanded into the
existing Prometheus `_bucket`, `_sum`, and `_count` series only after selecting
a compatible source; histogram rate functions remain raw-only. Subqueries
remain unsupported until nested step/accuracy context is propagated. A rollup
is eligible only when its width is no coarser than the requested step and its
coverage is finalized. The router splits only at recorded half-open coverage
boundaries and applies endpoint inclusion once at final projection; a coverage
gap produces an explicit insufficient-retention error.

This requires extending the current `Metric` model and OTLP decoder. Today it
does not retain `start_time_unix_nano` or Sum `is_monotonic`, so a correct
counter rollup cannot be implemented by aggregating the existing `value`
column alone. Exponential histograms remain explicitly unsupported unless the
target contract adds their storage and rollup semantics. The mapping is
explicit: a valid OTLP `start_time_unix_nano` becomes nullable
`TIMESTAMPTZ start_time`; `is_monotonic` is populated only for Sum and is NULL
for gauge/histogram/summary; temporality is stored as an enum-like text value
(`DELTA`, `CUMULATIVE`, or `UNSPECIFIED`); and an absent histogram sum remains
SQL NULL. Histogram `explicit_bounds` and `bucket_counts` are nullable because
OTLP permits a histogram with only count/sum; a distribution rollup is enabled
only when both are present and structurally valid. Histogram and summary flags
are stored verbatim, and the raw scalar row keeps either the original signed
integer or the original double (`value_kind`, `value_int`, `value_double`)
instead of silently coercing large integers to `DOUBLE`. The decoder rejects
zero/out-of-range event timestamps before any row is constructed.

`metric_postings` is a series dictionary/index, not an event-time sample
table; it is deliberately hash-partitioned and has a separate compaction
contract. Its logical uniqueness key is
`(series_id, segment_id, label_name, label_value, generation)`, and only one
visible generation may exist for a key at a DuckLake snapshot. Posting rows
are append-only versions: a label/segment lifecycle update closes the prior
version with `end_snapshot` and inserts a new version in one transaction.
Rows are retained while any sample coverage references their series segment;
after that, a separate postings-retention job may close and purge them.
The exact visibility predicate is
`begin_snapshot <= S AND (end_snapshot IS NULL OR S < end_snapshot)`; readers
select the greatest visible generation for the logical key
`(series_id, segment_id, label_name, label_value)` and never union generations.
The postings writer claims that logical key with the same
`compare_and_set(current_generation, current_lease_token)` protocol as
rollups, allocates `generation + 1` and an operation id, and closes the prior
generation only while holding the lease. A retry with the same operation id
reuses its committed generation; a stale lease aborts. A new key starts at
generation 1. This gives one active generation per posting key even when
series discovery, rebuild, or query-index maintenance races. Rows are
retained while any sample coverage references their series segment; after
that, a separate postings-retention job may close and purge them. Postings
compaction has its own file-creation watermark and never uses the sample-table
`record_date` TWCS policy.

The writer conditionally claims this row, records the operation id, and in the
same DuckLake transaction inserts the operation row, closes the prior posting
version, and inserts the new one. A retry first looks up `operation_id` and
returns the committed generation if present; an uncommitted operation may be
resumed only by its lease holder. The unique state key prevents two active
generations, and the operation table plus lease-token precondition make
retries and stale workers deterministic.

Every time-series sample table is date-partitioned before its first insert.
`series_key` is the canonical length-prefixed encoding of metric name, unit,
and sorted final Prometheus labels; `series_id` is its versioned SHA-256
base64url identifier. The index stores `series_key` so a hash collision is
detected and rejected rather than silently merging two series. Rollup
exemplars are capped at 32 per bucket, deduplicated by
`(trace_id, span_id, exemplar_timestamp, value)`, and selected in descending
exemplar timestamp order with `(trace_id, span_id, value)` as the deterministic
tie-break. Summary datapoints have no OTLP exemplar field; their absence from
`metric_summary_samples` is intentional and is part of the protocol.

Logical constraints are part of the schema contract: `value_kind = 'int'`
requires `value_int IS NOT NULL AND value_double IS NULL`, while
`value_kind = 'double'` requires the reverse; histogram distribution rows
require `length(bucket_counts) = length(explicit_bounds) + 1` and strictly
increasing bounds; and every table's logical key is unique for one visible
generation. These constraints are validated by the writer even if a
particular DuckLake catalog does not enforce all of them as SQL constraints.

Rollup state is sufficient to recompute a bucket and identify the source
snapshot/range that produced it. A single `value` column is not sufficient for
counters or histograms. The three scalar tables and three histogram tables are
separate physical tables with the concrete schemas shown above, not one
polymorphic table.

Each raw and rollup row carries the metric metadata needed by the existing
Prometheus metadata path: `metric_name`, `unit`, `description`, `attributes`,
and `resource_attributes`. A rollup copies these fields from the
event-time-last source row in its bucket (ties use the raw row's stable
ingestion key), while `metric_postings` supplies the canonical label index.
Consequently rollup queries do not depend on an implicit join back to another
raw table; metadata changes create a new raw row and are visible
through the corresponding bucket generation.

Rollup rows use snapshot visibility columns `begin_snapshot` and
`end_snapshot`. A row is visible at DuckLake snapshot `S` exactly when
`begin_snapshot <= S AND (end_snapshot IS NULL OR S < end_snapshot)`. The
idempotency key is `(scope, table, series_id, segment_id, bucket_start,
generation)`. A correction inserts a new generation and closes the prior
generation at the new snapshot in the same DuckLake transaction. Readers
select the greatest visible generation for `(series_id, segment_id,
bucket_start)` and never union generations. The generation key is also
recorded in the control store for recovery and idempotent retries. Before a
rewrite, the rollup worker atomically claims the unique bucket-state row with
`compare_and_set(current_generation, current_lease_token)`, allocates
`generation + 1`, and records an operation id. Only the lease holder may
close the current generation; a retry with the same operation id reuses the
committed generation, while a stale token aborts. This guarantees at most one
active generation per bucket even when two rollup workers race.

The state is durable DuckLake catalog data, not process-local memory. The
minimum control schema is:

```text
metric_rollup_state(
  scope TEXT, table_name TEXT, series_id TEXT, segment_id TEXT,
  level TEXT, bucket_start TIMESTAMPTZ, current_generation UBIGINT NOT NULL,
  current_lease_token TEXT NULL, current_operation_id TEXT NULL,
  source_snapshot_min UBIGINT NULL, source_snapshot_max UBIGINT NULL,
  dirty BOOLEAN NOT NULL, finalized BOOLEAN NOT NULL,
  PRIMARY KEY(scope, table_name, series_id, segment_id, level, bucket_start)
)

metric_rollup_operations(
  operation_id TEXT PRIMARY KEY, scope TEXT NOT NULL, table_name TEXT NOT NULL,
  series_id TEXT NOT NULL, segment_id TEXT NOT NULL, level TEXT NOT NULL,
  bucket_start TIMESTAMPTZ NOT NULL, allocated_generation UBIGINT NOT NULL,
  status TEXT NOT NULL, committed_snapshot UBIGINT NULL
)
```

The worker claims a state row with a conditional update on
`current_generation` and `current_lease_token`; zero updated rows means
retry or abort. It inserts the operation row under the unique `operation_id`,
then, in one DuckLake transaction, closes the old visible rollup row, inserts
the new generation, marks the operation committed, and updates the state row.
The commit precondition includes the claimed lease token. A retry first looks
up `operation_id`: committed returns the recorded generation, while an
uncommitted operation may be resumed only by its lease holder. This is the
durable transaction protocol behind the abbreviated CAS wording above.

Rollup is a separate semantic pipeline from file compaction:

1. Read a finalized source range at a pinned DuckLake snapshot. Finalization
   requires an explicit allowed-lateness policy (for example, a delay after
   `bucket_end`) and a correction window for late points; “finalized” cannot
   be an implicit assumption.
2. Group by stable series identity (metric name plus canonical labels) and
   event-time bucket.
3. Apply the fixed level-specific operators:
   - gauges select the last non-NaN sample by event time for the canonical
     value and also retain first/min/max/sum/count state for explicit query
     operators; an all-NaN bucket emits the staleness marker;
   - delta sums add values within the bucket; cumulative monotonic sums use
     ordered start/end values, detect a reset when the value decreases or the
     start time changes, and accumulate only valid segment increases;
     cumulative non-monotonic sums retain signed first/last changes and are
     not presented as counters;
   - histograms merge only rows with identical bounds; delta buckets/count/sum
     are added, while cumulative rows are differenced with the same reset
     rules. A bounds or temporality change starts a new compatible series
     segment and is never merged across;
   - summaries remain raw-only because quantiles cannot be combined safely
     without a mergeable sketch. Exemplar rollups retain a deterministic
     bounded representative set per bucket while raw exemplars remain intact.
     NaN and staleness counts are preserved in rollup state.
4. Write each level idempotently and maintain a rollup watermark containing
   source snapshot, event-time range, and level. A late raw point reopens or
   corrects the affected bucket; it is not a compaction retry.
5. Compact each target table's files independently with that table's own
   `newer_than` watermark. Compaction rewrites rows only; it never aggregates,
   drops, or changes their metric meaning.

Rollup finalization is per level, not global. Configuration must provide an
allowed-lateness delay and correction horizon for every enabled resolution.
There are no implicit production defaults: startup validation rejects an
enabled level whose two durations are absent, non-positive, or whose
correction horizon is shorter than its allowed-lateness delay.
For level `L`, a bucket is eligible only when
`bucket_end <= now - allowed_lateness[L]`. The correction horizon is measured
from `bucket_end`: a late point may correct the bucket only while
`now <= bucket_end + correction_horizon[L]`. Such a point marks the bucket
dirty and causes a new generation to be written atomically; readers select the
latest generation visible at their snapshot. A point arriving after that
horizon is retained in raw storage and reported as requiring repair
rather than silently changing a finalized rollup. Rollup state records level,
source snapshot, covered event-time range, generation, dirty buckets, and
finalization status.

These rollup watermarks are independent of the DuckLake compaction watermark
(file-creation time), and both are independent of retention. A successful
Parquet rewrite must never advance rollup coverage or permit raw data to be
deleted.

### Direct metric cutover

There are no existing users, so this deployment initializes the canonical
schema directly. There is no compatibility phase, dual-write period, or
historical-data path. Create `metric_samples` and its explicitly
date-partitioned rollup/index tables as part of normal catalog initialization,
before the first metric write. This release requires a clean catalog; old
schemas are unsupported and are not rewritten. The writer then publishes raw
metric samples directly to the canonical target family; asynchronous workers
populate the 5m/1h/1d tables and postings.

Remove the obsolete wide-table schema, its widening logic, its maintenance
entry, and all tests/documentation describing it. Keep `union_metrics` and
`committed_metrics` only as compatibility relations over the canonical family.
Initialize a clean catalog with the canonical schema. No old data is read,
renamed, migrated, or backfilled.

The direct-cutover transaction contract is intentionally simple: create and
partition every target table, verify the partition metadata, then let the
normal raw writer publish metric samples. Rollup workers and compaction use
the independent state/watermark contracts above. No historical source-selection
logic is needed for this no-user deployment.

to the exact DuckDB core commit used by thelake. The build must inherit the
upstream commit containing `newer_than`; do not reimplement that upstream
candidate filter. The current Rust crate expects
DuckDB 1.5.5 (`duckdb = 1.10505.0`) and dynamically links a packaged
`libduckdb`; therefore the build must package the fork-built DuckDB library
and extension together. `INSTALL ducklake` must not silently fetch the public
extension in production.

Add build checks that assert:

- DuckDB core ABI/version matches the Rust crate;
- the loaded DuckLake extension exposes the fork capability marker and
  accepts `newer_than` and the native TWCS parameters on
  `ducklake_merge_adjacent_files`;
- the interactive DuckDB shell uses the same library/extension pair as the
  runtime image.

Upstream contribution can be pursued in parallel, but production ownership
stays with Softprobe until upstream accepts the catalog codec contract,
external-catalog VARIANT semantics, and the TWCS policy. The fork should carry
only the VARIANT-inlining and native-TWCS changes that are not already
available upstream; do not fork or reimplement `newer_than`.

### Rollout

1. Ship the fork with inline VARIANT disabled by default; exercise codec
   round-trip and mixed-tier reads in CI.
2. Enable inline VARIANT for SQLite test catalogs and a canary PostgreSQL
   tenant; monitor read errors, inline table growth, query latency, and
   Parquet-file creation.
3. Enable incremental compaction for the canonical raw and rollup metric
   tables with persisted per-table watermarks and compare candidate counts,
   output partition invariants, and maintenance p95.
4. Enable production defaults only after the mixed-tier, maintenance,
   concurrency, and rollback tests pass.

Existing MAP → VARIANT conversion remains operator-owned. New inline rows use
DLV1 and the reader merges both tiers logically.

Old readers must be prevented from opening a catalog containing DLV1 inline
VARIANT fragments. Capability/version checks happen before reads and writes;
they fail with an actionable upgrade message. A missing marker remains
compatible only when no DLV1 fragments are present.

## Acceptance criteria for this design

- One fork and one build artifact provide the VARIANT capability and consume
  upstream incremental compaction.
- No application-side copy of DuckLake's file-selection or compaction
  algorithm is required.
- Inline VARIANT values are lossless, versioned, safely decoded, and visible
  through the same logical query surface as Parquet VARIANT values.
- Inline and Parquet stats share one collector/serialization rule and have
  distinct, queryable source keys.
- Incremental compaction uses the official `newer_than` candidate filter and
  preserves partition locality without a Rust TWCS planner or wave loop.
- Canonical metric ingestion writes only the raw/high-resolution target table
  family; asynchronous rollup workers populate the 5m/1h/1d target families.
- Every time-series target table is explicitly partitioned by `record_date`
  before its first insert, and the query planner selects resolutions without
  double-counting boundary samples.
- Metrics distinguish ingest snapshots, compaction snapshots, Parquet-file
  count, metadata SQL count, maintenance wall time, and object-store bytes;
  no claim attributes snapshot-count reduction to inlining alone.
